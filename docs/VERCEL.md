# نشر Hessara على Vercel

يستخدم فرع `deployment/vercel` تطبيق Next.js واحدًا للواجهة ونقاط API، وSupabase للمصادقة وPostgreSQL لحفظ التجارب واتصالات النماذج. هذا الدليل يصف خطوات الإعداد والتحقق، ولا يُعد سجلًا لنجاح نشر فعلي أو إعلانًا عن رابط Vercel جاهز.

تبقى نسخة Sites الحالية على مسارها السابق. قاعدة Supabase الجديدة مستقلة، ولا يستورد هذا الفرع حسابات Sites أو تجاربها أو مفاتيحها. يتطلب أي نقل لاحق للبيانات خطة منفصلة لربط هويات المستخدمين وإعادة تشفير المفاتيح عند الحاجة.

## ١. إعداد البيئات

استخدم مشروع Supabase للإنتاج ومشروعًا آخر للتطوير واختبارات التكامل. لا تربط معاينات الفروع غير الموثوقة بقاعدة الإنتاج أو أسرارها. يحتاج المشروع إلى Node.js 22.13 أو أحدث.

للتطوير المحلي من جذر المشروع:

```powershell
npm ci
Copy-Item .env.example .env.local
```

يقرأ Next.js ملف `.env.local`، ويقرأه أمر ترحيل قاعدة البيانات أيضًا. الملف مستثنى من Git. في Vercel، تُضاف القيم إلى إعدادات متغيرات البيئة المناسبة بدل رفع الملف.

| المتغير | القيمة والغرض |
| --- | --- |
| `DATABASE_URL` | رابط PostgreSQL السري من مشروع Supabase الصحيح. يستخدم التطبيق `POSTGRES_URL` بديلًا فقط عند غياب هذا المتغير. |
| `DATABASE_SSL_CA` | اختياري: نص شهادة CA العامة بصيغة PEM من إعدادات قاعدة Supabase عند الحاجة للتحقق من شهادتها. يقبل عدة أسطر أو فواصل `\n` مكتوبة حرفيًا؛ لا تضع مفتاحًا خاصًا هنا. |
| `NEXT_PUBLIC_SUPABASE_URL` | عنوان مشروع Supabase المستخدم للمصادقة. |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | المفتاح القابل للنشر للمشروع نفسه؛ لا تستخدم مفتاح `service_role` أو مفتاحًا سريًا مكانه. |
| `SUPABASE_AUTH_SECRET_KEY` | مفتاح Supabase سري بصيغة `sb_secret_…` للاستخدام على الخادم فقط، مطلوب لإعداد المصادقة على Vercel. لا تضعه في أي متغير يبدأ بـ `NEXT_PUBLIC_`. |
| `HESSARA_AUTH_IP_FORWARDING` | `true` على Vercel بعد تفعيل `security_sb_forwarded_for_enabled` في إعدادات Supabase Auth والتحقق من عملها. |
| `HESSARA_ENCRYPTION_KEY` | مفتاح ثابت من 32 بايت عشوائية، مُرمّز بصيغة Base64، لحماية مفاتيح النماذج المخزنة. |
| `HESSARA_SITE_URL` | أصل الموقع الكامل، مثل `http://localhost:5173` للتطوير، وعنوان HTTPS الفعلي للإنتاج؛ دون مسار إضافي. |
| `HESSARA_ALLOW_GUESTS` | `true` بعد تفعيل الدخول المجهول في Supabase، أو `false` لتعطيله في واجهة التطبيق. |
| `HESSARA_EMAIL_AUTH_ENABLED` | `true` فقط بعد إعداد البريد وSMTP واختبار تسليم رابط الدخول والعودة إلى الموقع. |
| `HESSARA_SHARED_MODEL_OWNER_ID` | اختياري: معرّف مستخدم Supabase الوحيد المسموح له باستخدام مفاتيح المزودين الموجودة في بيئة الخادم. |

متغيرا `NEXT_PUBLIC_` معلومتان عامتان مقصودتان؛ بقية الأسرار تبقى على الخادم. استخدم مفاتيح تشفير مختلفة للبيئات المنفصلة، واحتفظ بمفتاح الإنتاج في مخزن أسرار مع نسخة احتياطية مؤمّنة. يمكن توليده محليًا بهذا الأمر؛ لا تنشر مخرجاته:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

تغيير المفتاح بعد حفظ الاتصالات يمنع فك تشفير مفاتيح المستخدمين السابقة. تدويره يحتاج إعادة تشفير مدروسة، ولا يتحقق بمجرد استبدال المتغير.

## ٢. ربط قاعدة البيانات

انسخ رابط الاتصال من نافذة **Connect** داخل مشروع Supabase، واختر **Transaction pooler** لاتصال التطبيق على Vercel. احتفظ باسم المضيف والمنفذ كما أعادتهما الخدمة؛ لا تستنتجهما من المنطقة أو اسم المشروع. استخدم حساب التطبيق المخصص `hessara_runtime`، ويكون اسم المستخدم في التجميع المشترك `hessara_runtime.<project-ref>`، مع كلمة مروره وترميز محارف URL المحجوزة. توضح [وثائق الاتصال الرسمية](https://supabase.com/docs/guides/database/connecting-to-postgres) الفروق بين الاتصال المباشر وتجميع الاتصالات.

يستخدم التطبيق اتصالًا واحدًا لكل نسخة خادم، ويعطل العبارات المحضّرة لتوافق التجميع. يجري اتصال الإنتاج عبر TLS مع التحقق من الشهادة واسم المضيف؛ لا تعالج أخطاء الشهادات بإيقاف التحقق. إذا ظهر `SELF_SIGNED_CERT_IN_CHAIN`، نزّل شهادة CA من **Database Settings → SSL Configuration** في لوحة Supabase الموثوقة، ثم ضع محتوى PEM الكامل في `DATABASE_SSL_CA` للتطبيق ولعملية الترحيل عند الحاجة. الشهادة عامة، ويظل التحقق مفعّلًا عند استخدامها. راجع [دليل شهادات Supabase](https://supabase.com/docs/guides/platform/ssl-enforcement). يقتصر استثناء TLS في الشيفرة على عناوين localhost.

طبّق المخطط عبر اتصال إداري بالمشروع المقصود. إذا استخدمت الأمر التالي، مرّر رابط الإدارة في `DATABASE_URL` لهذه العملية وحدها، ولا تحفظه في إعدادات تشغيل Vercel:

```sh
npm run db:migrate
```

الأمر ينشئ جداول التجارب والنتائج والاتصالات والتكاملات وحدود الاستخدام داخل معاملة، ويستخدم قفل ترحيل لمنع التنفيذ المتزامن. لا يستورد ملفات D1 ولا بيانات Sites. يمكن تطبيق المخطط الأولي مرة أخرى دون حذف الجداول، لكنه ليس بديلًا عن ترحيلات مستقبلية مستقلة عند تغيير المخطط.

بعد المخطط، طبّق `supabase/runtime-role.sql` مرة واحدة بالاتصال الإداري داخل معاملة. ينشئ الملف دورًا بلا تسجيل دخول أو كلمة مرور، ويمنحه القراءة والكتابة على جداول التطبيق الستة فقط وسياسات RLS مخصصة له. فعّل `LOGIN` وعيّن كلمة مرور عشوائية عبر مسار آمن مستقل، ثم ضع رابط هذا الدور في `DATABASE_URL` على Vercel. لا تحفظ كلمة المرور في SQL أو Git، ولا تمنح الدور عضوية أدوار Supabase أو تمنحه إلى `authenticator`. يتوقف الملف إذا كان الدور موجودًا حتى تُراجع صلاحياته. نفّذ جميع الترحيلات اللاحقة بالاتصال الإداري؛ حساب التشغيل لا يملك صلاحيات تغيير المخطط.

تُفعّل الترحيلة RLS وتمنع أدوار `anon` و`authenticated` من الوصول المباشر إلى جداول التطبيق. يصل الخادم إليها عبر اتصال قاعدة البيانات الخاص، بعد التحقق من هوية المستخدم وملكية الصفوف. لا تضف سياسة وصول عامة لحل مشكلة مصادقة أو اتصال.

## ٣. تفعيل تسجيل الدخول

يلزم تفعيل مسار دخول واحد على الأقل ليستطيع الزائر حفظ التجارب وتشغيلها. لا تعتمد هذه النسخة على تسجيل الدخول عبر Sites، ولا تقبل رؤوس `oai-authenticated-user-*` بوصفها إثبات هوية.

على Vercel، تمر طلبات المصادقة عبر خوادم مشتركة. يتطلب النشر إعداد تمرير عنوان الزائر الموثوق إلى Supabase حتى لا تطبق حصة عنوان خادم واحد على جميع الزوار: فعّل `security_sb_forwarded_for_enabled` في إعدادات Supabase Auth، وأضف `SUPABASE_AUTH_SECRET_KEY` إلى بيئة الخادم، ثم اضبط `HESSARA_AUTH_IP_FORWARDING=true`. تغيير المتغير وحده لا يفعّل إعداد Supabase. تعامل مع المفتاح السري كاعتماد إداري، ولا تضعه في الواجهة أو تقارير الاختبار أو السجلات.

لا تُعد المصادقة جاهزة على Vercel إذا غابت متطلبات هذا الإعداد. يسمح التطوير المحلي بالاتصال بالمفتاح القابل للنشر دون تمرير العناوين؛ لذلك لا يكفي نجاح الدخول محليًا للتحقق من إعداد الإنتاج.

**دخول الضيوف:** فعّل Anonymous Sign-Ins في Supabase ثم اضبط `HESSARA_ALLOW_GUESTS=true`. يحصل الضيف على هوية مستقلة وجلسة خاصة بمتصفحه. حذف بيانات المتصفح أو تسجيل الخروج قد يفقده الوصول إلى تجاربه؛ يمكن ربط الجلسة ببريد مؤكد لاحقًا عند إتاحة البريد. لا تعادل الجلسة حسابًا قابلًا للاسترجاع من أي جهاز. راجع [وثائق الدخول المجهول](https://supabase.com/docs/guides/auth/auth-anonymous).

**الدخول بالبريد:** جهّز مزود SMTP وأكمل إعداد المرسل في Supabase، ثم اختبر التسليم إلى عنوان خارج فريق المشروع قبل ضبط `HESSARA_EMAIL_AUTH_ENABLED=true`. خدمة البريد الافتراضية في Supabase مقيدة وليست مناسبة لدخول الجمهور؛ وجود عنوان Supabase ومفتاحه العام وحدهما لا يجعل البريد جاهزًا. راجع [إعداد SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

في إعدادات Supabase الخاصة بعناوين المصادقة:

1. اجعل **Site URL** مساويًا لعنوان الإنتاج في `HESSARA_SITE_URL`.
2. أضف عنوان العودة الفعلي على النطاق نفسه إلى **Redirect URLs**: المسار المستخدم هو `/auth/callback`، وقد يتضمن معامل `next` للعودة إلى صفحة داخلية. طابق الرابط الذي يرسله التطبيق، واختبره من البريد حتى تكتمل الجلسة.
3. أضف عنوان التطوير `http://localhost:5173/auth/callback` إلى مشروع الاختبار فقط، مع السماح بمعامل العودة عند الحاجة. استخدم نطاقات المعاينة المحددة لمشروعك؛ لا تسمح بجميع نطاقات `vercel.app` في مشروع الإنتاج.
4. اختبر الرابط من المتصفح نفسه الذي بدأ طلب الدخول، لأن تدفق PKCE يعتمد على ملفات تعريف الارتباط الخاصة بتلك الجلسة.

اضبط إعدادات عناوين العودة وفق [دليل Supabase الرسمي](https://supabase.com/docs/guides/auth/redirect-urls). تحتفظ الواجهة بمسارات العودة الداخلية فقط وتمنع العودة إلى مواقع خارجية.

## ٤. إعداد مشروع Vercel

استورد المستودع وحدد فرع `deployment/vercel` للنشر المقصود. اضبط مجلد الجذر على المجلد الذي يحتوي `package.json`، واختر Next.js. يحتوي `vercel.json` على:

| الإعداد | القيمة |
| --- | --- |
| أمر التثبيت | `npm ci` |
| أمر البناء | `npm run build` |
| مجلد المخرجات | `.next` |

أضف متغيرات البيئة قبل البناء، ثم اضبط `HESSARA_SITE_URL` وعناوين المصادقة على النطاق الفعلي الذي خصصه Vercel للمشروع. أعد النشر بعد تعديل المتغيرات؛ خصوصًا قيم `NEXT_PUBLIC_` التي تدخل في البناء. أمر البناء لا يطبق ترحيل قاعدة البيانات تلقائيًا.

تحتاج مسارات التقييم المطوّلة إلى دعم مدة تنفيذ تصل إلى 120 ثانية كما تحددها الشيفرة. تحقق من إعدادات الوظائف وخطة الحساب المستخدمة قبل تشغيل نماذج تتطلب مهلة طويلة. تحتفظ المنصة بنتائجها في PostgreSQL؛ لا تعتمد على بقاء ملفات محلية أو عملية خادم واحدة بين الطلبات.

مفاتيح OpenAI وAnthropic وGemini الاختيارية الموجودة في `.env.example` لا تُشارك تلقائيًا مع الزوار. يطابق الخادم `HESSARA_SHARED_MODEL_OWNER_ID` مع هوية Supabase المؤكدة قبل استخدامها. يربط بقية المستخدمين مفاتيحهم من واجهة المنصة، وتبقى التكلفة والحصص خاضعة لمزودي النماذج. المحاكاة لا تحتاج مفتاح مزود.

## ٥. التحقق قبل مشاركة الرابط

شغّل الفحوص من جذر المشروع:

```sh
npm test
npm run typecheck
npm run build
```

لا تحتاج الاختبارات المعزولة إلى قاعدة الإنتاج. لا تثبت نتيجة البناء وحدها نجاح تسجيل الدخول أو الاتصال بقاعدة بيانات مستضافة.

لاختبار واجهة API، شغّل `npm run dev` بملف `.env.local` يشير إلى **مشروع Supabase تجريبي مستقل**، مع تفعيل دخول الضيوف وترحيل المخطط ومفتاح تشفير تجريبي. اترك إعدادات Paperclip الحقيقية فارغة، ثم نفّذ من نافذة أخرى:

```sh
node tests/local-api.mjs
```

يقيد هذا الاختبار عنوان التطبيق بـ localhost، لكن قاعدة البيانات قد تكون بعيدة؛ تحقق من عنوانها قبل التنفيذ. ينشئ الاختبار ضيوفًا وتجارب محاكاة واتصالات بمفاتيح وهمية، ولا يتصل بمزود نماذج مدفوع. يكتب بيانات فعلية في قاعدة الاختبار ولا يزيلها كلها تلقائيًا. لا تشغّله عبر خادم محلي متصل بقاعدة الإنتاج.

بعد النشر، تحقق من هذه المسارات على رابط Vercel الفعلي:

- تظهر الصفحة والأدلة على الهاتف والحاسوب، ولا تعترض حماية معاينة Vercel دخول الزائر إلى نشر الإنتاج العام.
- يعيد `/api/health` حالة `ready` ورمز 200؛ هذا فحص إعداد واتصال أولي، وليس اختبارًا كاملًا للبريد أو المزودين.
- تنجح الجلسة المختارة، ثم تكتمل تجربة محاكاة صغيرة وتبقى نتائجها بعد إعادة تحميل الصفحة.
- لا تستطيع جلسة أخرى قراءة تجربة المستخدم الأول أو اتصالاته المحفوظة.
- يصل رابط البريد ويعيد المستخدم إلى الجلسة الصحيحة إذا كان مسار البريد مفعّلًا.
- يصدر التقرير بنجاح، وتظهر أخطاء الربط أو الحصص بوضوح عند اختبار مزود فعلي بمفتاح مخصص لذلك.

تظل نسخة Sites متاحة أثناء التحقق. إعادة نشر إصدار سابق في Vercel لا تعيد قاعدة البيانات إلى حالتها القديمة؛ راجع توافق المخطط واحتفظ بنسخ احتياطية مستقلة قبل أي ترحيل مستقبلي.
